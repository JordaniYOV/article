# Planetary Eval — React

Интерфейс оценки одной модели за запуск: подключение датасетов, конфигурации
SpaceLLaVA и NASA–IBM, искажения и их комбинации, очередь, ответы, карты и метрики.
React + TypeScript + Vite, графики Recharts. Отдельный FastAPI worker выполняет
обработку; браузер получает состояние через API каждые 3 секунды.

## Запуск

Нужен Node.js 22.12+ (или 20.19+). Из корня проекта:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

Открыть [http://127.0.0.1:5173](http://127.0.0.1:5173).
В двух других терминалах, из корня проекта:

```powershell
& .\.venv-benchmark\Scripts\python.exe -m uvicorn api.main:app --reload --host 127.0.0.1 --port 8000
```

```powershell
& .\.venv-benchmark\Scripts\python.exe -m api.worker
```

Установка Python-зависимостей описана в [инструкции API](../src/api/README.md).
Без worker задания остаются в очереди. Запуск сайта не скачивает веса.
Реальные модели требуют локальных весов, зависимостей и отдельного smoke test.

## Настройка адресов

Vite пересылает `/api/*` на `http://127.0.0.1:8000/*`, включая снимки и карты.
Для другого адреса скопируйте `.env.example` в `.env.local` и задайте
`VITE_API_PROXY_TARGET`. Перезапустите Vite после изменения переменных.

`VITE_API_BASE_URL` нужен только при прямом обращении браузера к другому серверу;
тогда разрешите origin фронтенда в `PLANETARY_API_CORS_ORIGINS` бэкенда.

Production-сборка: `npm.cmd run build`; локальная проверка сборки:
`npm.cmd run preview` ([порт 4173](http://127.0.0.1:4173)). Для размещения
отдавайте `dist/` и настройте reverse proxy `/api/` к FastAPI со снятием префикса.
Прокси Vite работает только при `dev`/`preview`, его нет внутри `dist/`.
Текущая версия рассчитана на локальное использование и не добавляет авторизацию.

## Работа в интерфейсе

1. **Датасет.** Загрузите ZIP со снимками и `manifest.jsonl`, укажите прямую
   ссылку на ZIP или подключите существующий manifest внутри `data_orbital/`.
   Структура и поля разметки — в [инструкции загрузки](../src/api/README.md#загрузка-zip).
   GT используется только для оценки. Для NASA–IBM требуется предусмотренный
   бэкендом lunar IMP протокол входа, произвольный PNG не гарантирует совместимость.
2. **Модель.** Нажмите «Подключить конфигурации проекта». Готовые конфигурации
   выключены: настройте локальные пути и включите модель через значок настроек.
   Можно загрузить JSON конфигурации или создать её вручную. Веса загружает
   worker, файл весов через браузер не принимается. Поддерживаются адаптеры
   `spacellava`, `ibm_imp`, а для технической проверки — `mock`.
   После появления запусков конфигурация фиксируется; для изменений нужна новая версия.
3. **Сбор ответов.** Выберите одну модель, датасет, число снимков, split, seed,
   эффекты и порядок комбинаций. В дополнительных параметрах задаются сила
   искажений, вопрос и допустимые ответы. Четыре эффекта и общая комбинация
   дают пять искажённых условий; оригинал добавляет шестое условие.
   SpaceLLaVA отправляется в `/vlm/runs`, IBM — в `/vit/runs`.
   В «Выберите датасет» всегда доступны **Марс** и **Луна**. Для каждой планеты
   отдельно выбираются снимки с масками или картами высот; для Луны есть IMP.
   Сервер сначала использует `data_orbital/orbital_300_v3/<planet>/` и проверяет
   хеши. Если нужных файлов нет, выбор датасета запускает их восстановление
   в фоне и показывает прогресс. Запуск модели доступен после подготовки.
   Кадры и источник split закреплены; число снимков ограничено размером split.
4. **История.** Состояние обновляется автоматически. Можно остановить или
   продолжить обработку. Остановка исполняется после текущего снимка.
5. **Метрики.** После завершения нажмите «Рассчитать метрики». Для текстовых
   ответов Accuracy/F1 требуют допустимых вариантов и GT; свободные описания
   сейчас не имеют автоматической оценки качества. Для IMP показываются
   IoU, Dice и pixel accuracy. Недоступные показатели отображаются как «—».
6. **Сравнение.** Вторую модель запускайте через «Повторить выборку», выбрав
   первый запуск. Сервер закрепляет одинаковые снимки и параметры; затем
   выберите второй запуск в результатах. Разные определения качества VLM и
   ViT не дают общей шкалы. Отчёт сохраняется в JSON, таблица — в CSV.
7. **Ответы.** Вкладка показывает обработанный снимок, исходный текст или
   наложение предсказанной IMP карты. Это предсказание модели, не GT.

SQLite хранит конфигурации, очередь, результаты и анализ метрик. Снимки и
артефакты остаются на сервере в `data_orbital/` и
`outputs/<название модели>/<run_id>/`. Фронтенд не подключается к SQLite напрямую.
Состояние незапущенной формы не сохраняется после перезагрузки страницы.

Пример JSON конфигурации для технической проверки без GPU:

```json
{
  "name": "UI-smoke-test",
  "version": "v1",
  "model_id": "fixture/mock",
  "backend": "mock",
  "enabled": true,
  "options": { "default_response": "YES" },
  "max_new_tokens": 128,
  "seed": 42
}
```

Такие ответы и графики обозначены как тестовые и не являются научными результатами.

## Проверка

```powershell
npm.cmd test
npm.cmd run build
```

Тесты проверяют тело запросов VLM/ViT, ZIP и URL загрузку, ошибки API,
повторение протокола, выключенные модели, расчёт/отображение метрик и отсутствие
выдуманных значений. Тестовые данные находятся только в `src/test/` и не используются
как запасные ответы при отключённом бэкенде.
